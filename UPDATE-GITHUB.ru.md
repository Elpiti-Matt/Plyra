## 1. Разобраться с тремя окнами

В инструкции мы будем переключаться между ними:

| Окно | Для чего нужно |
| --- | --- |
| **Браузер** — Chrome, Edge, Safari и т.п. | Сайт GitHub, проверка изменений, объединение веток, публикация |
| **GitHub Desktop** — отдельная программа | Скачать репозиторий на компьютер, сохранить изменения и отправить их |
| **Проводник Windows / Finder на Mac** | Распаковать ZIP и скопировать файлы из одной папки в другую |

**Репозиторий** — проект с историей файлов. **Clone** создаёт его рабочую копию на компьютере. **Branch / ветка** — отдельная версия для подготовки изменений. **Commit** фиксирует изменения локально. **Push / Publish branch** отправляет их на GitHub. **Pull request / PR** — страница проверки и объединения ветки с `main`; **Merge** выполняет это объединение.

## 2. Скачать и распаковать обновление

1. Скачайте из переписки **Plyra-0.7.0-rc.4-github.zip**. Отдельный HTML нужен для быстрого запуска, ZIP — для обновления исходников.
2. В Проводнике нажмите ZIP правой кнопкой → **Извлечь всё… → Извлечь**. На Mac дважды нажмите ZIP.
3. Откройте распакованную папку, затем находящуюся в ней папку **Plyra**.
4. Внутри должны быть `src`, `docs`, `demo`, `package.json`, `README.md` и другие файлы. Эту папку далее называем **А — обновление**.

Для дополнительной копии старой версии откройте репозиторий в браузере: **Code → Download ZIP**. Сохраните его отдельно, например в папке «Plyra до обновления». Не распаковывайте старый ZIP поверх нового. Основная история также сохраняется в GitHub.

## 3. Установить GitHub Desktop и клонировать проект

1. Откройте [официальную загрузку GitHub Desktop](https://desktop.github.com/download/), выберите Windows или свой Mac, установите и запустите программу.
2. Нажмите **Sign in to GitHub.com**. В открывшемся браузере войдите в аккаунт, у которого есть доступ к `Elpiti-Matt/Plyra`. Завершите вход и вернитесь в Desktop.
3. В верхнем меню Desktop нажмите **File → Clone repository…**.
4. Выберите вкладку **URL**. В поле адреса вставьте:

   ```text
   https://github.com/Elpiti-Matt/Plyra
   ```

5. В **Local path** выберите место на компьютере. Например, `Документы/GitHub/Plyra`. Запомните путь. Нажмите **Clone** и дождитесь завершения.
6. Слева сверху в **Current repository** должно быть `Plyra`, рядом в **Current branch** — `main`.

Если проект уже клонирован в Desktop, выберите его в **Current repository** вместо повторного клонирования. На вкладке **Changes** не должно быть ваших несохранённых правок перед переносом; если они есть, сначала сохраните их в своей отдельной ветке. [Официальная инструкция клонирования](https://docs.github.com/en/desktop/adding-and-cloning-repositories/cloning-and-forking-repositories-from-github-desktop).

## 4. Создать ветку обновления

1. Находясь в `Plyra`, выберите **Current branch → main**.
2. Нажмите сверху **Fetch origin**. Если после этого появилась **Pull origin**, нажмите и её — это заберёт последние файлы с GitHub.
3. Нажмите **Current branch → New branch**.
4. Введите имя `update/plyra-0.7.0-rc.4`. Если спрашивается исходная ветка, выберите `main`.
5. Нажмите **Create branch**. Теперь сверху должно быть имя новой ветки.
6. Откройте **Repository → Show in Explorer** (Windows) или **Show in Finder** (Mac). Откроется рабочая папка проекта. Называем её **Б — репозиторий**.

Пока изменения существуют только в этой ветке на вашем компьютере. [Как работают ветки в Desktop](https://docs.github.com/en/desktop/making-changes-in-a-branch/managing-branches-in-github-desktop).

## 5. Исправить имя папки формы ошибок

В проверенном `main` папка называется `.github/issue_template`; GitHub распознаёт формы по пути `.github/ISSUE_TEMPLATE`. На Windows и некоторых Mac изменение только регистра может остаться незамеченным Git. Поэтому здесь два переименования с промежуточным сохранением.

1. В **папке Б** откройте `.github`. На Mac скрытые папки показывает **Cmd + Shift + .**; на Windows при необходимости включите отображение скрытых элементов.
2. Переименуйте `issue_template` в **ISSUE_TEMPLATE_TMP**. На Windows: выделить папку → F2 → новое имя → Enter; на Mac: выделить → Return → имя → Return.
3. Переключитесь в **GitHub Desktop → Changes**. Должны появиться изменения файлов этой папки.
4. Внизу слева найдите поле **Summary (required)**. Впишите `Prepare issue template folder rename` и нажмите **Commit to update/plyra-0.7.0-rc.4**. Это локальный промежуточный коммит; отправлять его отдельно не требуется.
5. Вернитесь в Проводник/Finder и переименуйте **ISSUE_TEMPLATE_TMP** в **ISSUE_TEMPLATE**.
6. В этой папке удалите пустой `test.txt`. Также удалите пустой `test.txt` из `.github/workflows`, если он есть. `bug_report.yml`, `ci.yml` и `pages.yml` не удаляйте — их обновит копирование.

Если после получения свежего `main` папка уже называется `ISSUE_TEMPLATE` и двух `test.txt` нет, этот раздел пропускается. Промежуточная папка `ISSUE_TEMPLATE_TMP` не должна остаться в готовом обновлении. [Расположение шаблонов Issues](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/about-issue-and-pull-request-templates).

## 6. Скопировать новые файлы

Проверьте, что открыты **две разные папки**:

| Папка | Пример расположения | Что с ней делать |
| --- | --- | --- |
| **А — обновление** | Загрузки → распакованный архив → Plyra | Отсюда копировать |
| **Б — репозиторий** | Документы → GitHub → Plyra | Сюда вставлять |

Обе папки могут называться `Plyra` — различайте их по полному пути сверху окна. В папке Б находится история Git; целиком очищать её не нужно.

**На Windows:**

1. Перейдите внутрь папки А, туда, где виден `package.json`.
2. Нажмите **Ctrl + A**, затем **Ctrl + C** — выделить всё содержимое и скопировать.
3. Перейдите внутрь папки Б, где уже находится её `package.json`.
4. Нажмите **Ctrl + V**. При вопросе о совпадающих файлах выберите **Заменить файлы в папке назначения**. Подтвердите объединение одноимённых папок, если Проводник спрашивает.

**На Mac:** покажите скрытые файлы через Cmd + Shift + ., копируйте содержимое А в Б через Cmd + C / Cmd + V. При совпадении **файлов** выбирайте замену. При совпадении **папок** выбирайте Merge / Объединить, если Finder предлагает. Если есть только замена папки целиком, откройте одноимённые папки и перенесите их содержимое; повторите для совпадающих вложенных папок. Так сохраняются дополнительные файлы рабочей копии.

В итоге `package.json` должен находиться прямо в Б. Не должно получиться `Б/Plyra/package.json`: это означало бы копирование внешней папки вместо её содержимого. Архив уже содержит `demo/index.html`, поэтому отдельно добавлять скачанный HTML в корень репозитория не требуется.

Если после нашей проверки в `main` появились ваши новые файлы или правки, сравните их в Desktop перед заменой. В проверенном коммите дополнительных `CNAME` и `REPOSITORY.json` не было; новый `REPOSITORY.json` настроен именно на `Elpiti-Matt/Plyra`.

## 7. Проверить результат на компьютере

1. Вернитесь в **GitHub Desktop → Changes**. Изменённых файлов будет много: приложение, документация, данные, картинки. Это ожидаемо для большого обновления.
2. Нажмите в списке `package.json`: новая версия должна быть **0.7.0-rc.4**. Красный текст — прежний, зелёный — добавленный.
3. Проверьте наличие новых `docs/FEATURES.ru.md`, `docs/images`, `scripts/build-ai.mjs`, а также `src/tool/OverviewCanvas.tsx`.
4. В `.github` должны остаться `ISSUE_TEMPLATE/bug_report.yml`, `workflows/ci.yml`, `workflows/pages.yml`. Старого `issue_template`, временного `ISSUE_TEMPLATE_TMP` и двух пустых `test.txt` быть не должно.
5. В папке Б откройте **demo → index.html** двойным нажатием. Если запускается редактор текста, нажмите правой кнопкой → **Открыть с помощью → Chrome/Edge/Firefox/Safari**. Корневой `index.html` предназначен для сборщика; автономный файл находится именно в `demo`.
6. В приложении откройте **Показ**: у типов узлов и типов связей должны быть свои **Выбрать все / Выключить все**.
7. Нажмите **− Все листы**, включите **Только для выделенного листа**, выберите другой лист за заголовок. Проверьте смену его имени над обзором.
8. В справке откройте подготовку проекта с ИИ: стандарт должен быть **Plyra v3** с `types.attributes` и значениями у узлов. Остальные сценарии перечислены в [START-HERE](START-HERE.ru.md).

Не копируйте в репозиторий `node_modules` и временные папки сборки. В новом архиве их нет. Проверка в Desktop позволяет просмотреть каждый файл до отправки. [Официальная справка о просмотре и коммитах](https://docs.github.com/en/desktop/making-changes-in-a-branch/committing-and-reviewing-changes-to-your-project-in-github-desktop).

## 8. Сохранить и отправить ветку

1. В **GitHub Desktop → Changes** оставьте отмеченными файлы этого обновления.
2. Внизу слева в **Summary (required)** введите `Update Plyra to 0.7.0-rc.4`.
3. Нажмите **Commit to update/plyra-0.7.0-rc.4**. После коммита список Changes должен опустеть.
4. Сверху нажмите **Publish branch**. Если ветка уже была отправлена раньше, кнопка называется **Push origin**. Дождитесь завершения.

Теперь новая ветка есть на GitHub. Основная ветка `main` и сайт ещё не обновлены.

## 9. Создать страницу проверки — Pull request

1. Нажмите **Create Pull Request** в Desktop, если кнопка появилась. Либо откройте [репозиторий в браузере](https://github.com/Elpiti-Matt/Plyra): **Pull requests → New pull request**.
2. Сверху проверьте **base: main** и **compare: update/plyra-0.7.0-rc.4**. Это означает «перенести подготовленное обновление в основную ветку».
3. Нажмите **Create pull request**. Заголовок: `Plyra 0.7.0-rc.4: editor and documentation update`.
4. В описание можно вставить:

   ```text
   Обновление Plyra до 0.7.0-rc.4.

   Добавлены словари типов/тегов, типизированные атрибуты, импорт базовой
   геометрии диаграмм, All-to-1 и обзор всех листов с независимыми позициями.
   В «Показ» появились отдельные групповые кнопки узлов и связей.
   В обзоре — связи только выделенного листа.
   Обновлены FAQ, AI-промпт v3, примеры, иллюстрации и документация.

   Локально: 98 тестов модели/DOM, TypeScript и автономная сборка.
   Проверить: успешный Checks и ручные сценарии START-HERE.ru.md.
   Визуальная проверка браузером в среде подготовки была заблокирована.
   ```

5. Подтвердите **Create pull request**. Откроется страница PR с вкладками Conversation, Commits, Checks и Files changed.

## 10. Дождаться проверок и обновить main

1. На странице PR найдите блок проверок или вкладку **Checks**. Workflow **Checks** устанавливает зависимости, запускает тесты и сборку. Это занимает несколько минут.
2. Дождитесь зелёного результата. Красный крест означает ошибку; откройте её шаг и сохраните текст ошибки для разбора. Если проверка не стартовала, откройте Actions и посмотрите сообщение GitHub.
3. Откройте **Files changed**. Убедитесь, что изменяется ваш проект и в него не добавилась лишняя вложенная папка `Plyra`.
4. Вернитесь в **Conversation**, нажмите **Merge pull request**, затем **Confirm merge**. Если GitHub требует дополнительную проверку или ревью, он укажет это рядом с кнопкой; выполните указанное условие.
5. После сообщения об успешном объединении новая версия находится в `main`. Кнопка **Delete branch** удаляет подготовительную ветку, сохраняя изменения и историю; её можно нажать.
6. В Desktop выберите **Current branch → main**, затем **Fetch origin → Pull origin**, если предложено. Рабочая папка получит объединённую версию.

## 11. Обновить сайт GitHub Pages

У вас уже есть успешные публикации Pages. Начните с существующего workflow; настраивать сайт заново обычно не требуется.

1. Откройте [Actions репозитория](https://github.com/Elpiti-Matt/Plyra/actions).
2. Слева выберите **Publish demo to GitHub Pages**.
3. Над списком запусков нажмите **Run workflow**.
4. В выборе ветки укажите **main**, затем ещё раз **Run workflow**.
5. Откройте появившийся запуск и дождитесь зелёного завершения. Он заново собирает приложение и публикует `dist`.
6. Откройте [сайт Plyra](https://elpiti-matt.github.io/Plyra/). Обновите страницу; при старой версии используйте Ctrl + Shift + R или Cmd + Shift + R и проверьте кнопки из шага 7.

Если запуск сообщает, что Pages не настроен, откройте **Settings → Pages → Build and deployment → Source** и проверьте **GitHub Actions**, затем повторите запуск. Закрытая страница настроек при подготовке не была доступна, но публичная история подтверждает прежнюю успешную публикацию.

`pages.yml` запускается вручную: один только коммит или Merge сайт не обновляет. [Ручной запуск workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) · [Pages через GitHub Actions](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## 12. Необязательно: сделать отдельный скачиваемый релиз

Исходники и сайт уже обновлены. Раздел Releases нужен дополнительно, чтобы посетитель мог скачать один HTML без поиска по папкам.

Откройте главную страницу репозитория → **Releases → Create a new release**. Создайте тег `v0.7.0-rc.4`, выберите Target `main`, название `Plyra 0.7.0-rc.4`. В описание вставьте перечень изменений из PR. Прикрепите **Plyra-0.7.0-rc.4.html**, отметьте **Set as a pre-release**, затем **Publish release**. RC — кандидат на выпуск, поэтому это предварительный релиз. Перед созданием убедитесь, что тег с таким именем ещё не появился.

## Если что-то пошло не так

| Ситуация | Следующее действие |
| --- | --- |
| В Desktop нет изменений после копирования | Проверьте **Repository → Show in Explorer/Finder**: туда ли вставлены файлы и открыта ли ветка обновления |
| В Changes появилась папка Plyra внутри проекта | Файлы попали на уровень глубже; верните их в корень Б до коммита |
| Не вижу кнопку Publish branch | После отправки её заменяет Push origin или Fetch origin; проверьте наличие ветки на GitHub |
| Checks красный | Откройте запуск → ошибочный шаг, скопируйте текст ошибки; исправление отправляется в ту же ветку тем же Commit / Push |
| Нет Run workflow | Проверьте, что выбран именно **Publish demo to GitHub Pages** и вы вошли в аккаунт с правом записи |
| Сайт старый после Merge | Выполните отдельный шаг публикации Pages, дождитесь успеха и обновите страницу |
| Ошибка обнаружилась после Merge | Откройте объединённый PR → **Revert**; GitHub подготовит обратный PR. Проверьте и объедините его, затем повторите публикацию Pages |

[Откат через Revert](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/reverting-a-pull-request) сохраняет историю. При конфликтах GitHub может потребовать ручного разрешения. До Merge можно просто оставить PR открытым и продолжить исправления в той же ветке.

Работа завершена, когда `main` содержит 0.7.0-rc.4, Checks зелёный, публикация Pages завершилась успешно, а на сайте доступны новые переключатели. Для обычного обновления не нужно создавать новый репозиторий или удалять старый.
