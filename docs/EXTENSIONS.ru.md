# Расширения, компоненты документов и первый публичный показ

Концепция следующего этапа, сверена с 0.7.0-rc.4 9 сентября 2026 года. Словари, атрибуты и базовые импорты draw.io, JSON Canvas и BPMN DI уже реализованы. Исполняемые пользовательские плагины, сборщик документов и CCMS пока не реализованы.

## Разделение уровней

| Уровень | Назначение | Минимальная следующая реализация |
|---|---|---|
| Граф | Постоянные ID объектов и отношения между ними | Сохранить различие между объектом, описывающей его диаграммой и размещением карточки |
| Словари | Типы объектов, связей, листов, теги и атрибуты | Реализованы в нативном JSON v3; следующий шаг — проверять их на реальных сценариях |
| Адаптеры | Получение артефактов из файлов | draw.io, JSON Canvas и BPMN DI уже импортируются; дальше — расширение покрытия и происхождение ревизий |
| Сборка документов | Повторное использование содержимого | Упорядоченный рецепт из ссылок на компоненты; предпросмотр; экспорт Markdown/HTML |
| Возможности CCMS | Управление жизненным циклом компонентов | Версии, согласование, варианты, переводы, права и публикации по реальному запросу |

Плагин — способ подключить возможность. CCMS — набор задач по управлению содержимым. Сборщик можно оформить как расширение, но один механизм плагинов не задаёт правила версий, переиспользования или публикации.

Сопоставление с DITA помогает объяснить идею: maps организуют материалы, а content references переиспользуют фрагменты. Это аналогия архитектуры, не утверждение о совместимости Plyra с DITA. [DITA maps](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/ditamaps.html), [content references](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/conref.html).

## Один рабочий эксперимент

В [примере разработки](../examples/software/README.ru.md) фрагмент о сроке доступности файла нужен двум инструкциям. Для первого сборщика достаточно:

1. Компонента с ID, содержимым, языком и версией.
2. Рецепта документа: упорядоченные ссылки на компоненты и выбранные версии. Координаты карточек и обычные связи не задают порядок документа.
3. Проверки отсутствующих ссылок, циклов включения и несовместимых версий.
4. Предпросмотра собранного документа с происхождением разделов.
5. Выгрузки Markdown/HTML с перечнем использованных версий.

Изменение компонента делает зависимые публикации кандидатами на пересборку. Оно не должно молча менять уже выпущенную версию документа. Для начала можно фиксировать версии при экспорте и пересобирать вручную.

Такой эксперимент может работать локально с файлами. Полный CCMS добавит существенно больше: редакционные процессы, разрешения, согласования, локализацию и историю публикаций. Их стоит вводить после проверки пользы переиспользования.

## Как подключать расширения

Текущая версия использует декларативные словари и встроенные адаптеры: распознать файл, прочитать, вернуть нормализованный граф и отчёт предпросмотра. Публичный SDK и загрузка исполняемых расширений остаются отдельными будущими задачами.

Стабилизировать контракт на двух реальных расширениях, затем выделять публичный SDK. Открытый SDK можно сочетать с собственными дополнительными пакетами под отдельно выбранными условиями, если права на эти пакеты позволяют это.

Произвольный сторонний JavaScript в странице редактора получает доступ к чувствительным данным приложения. Поэтому пользовательские исполняемые плагины требуют отдельной модели полномочий и изоляции; обычный Worker сам по себе не является достаточной границей безопасности. Это основание начать с данных и встроенных адаптеров.

## Когда показывать Hacker News

Для Show HN нужен продукт, который можно попробовать. Ранний этап допустим; регистрации, формы ожидания и прочие барьеры мешают обратной связи. Домен не указан как условие. Статья-разбор подаётся как обычная ссылка, работающий инструмент — как Show HN. [Правила Show HN](https://news.ycombinator.com/showhn.html).

Предлагаемый критерий готовности Plyra: английский путь от открытия демо до одного понятного результата; синтетический пример; работающие сохранение и повторное открытие; заметное объяснение общих узлов; честно названные ограничения. В подготовленной версии есть полный английский набор, но стартовое демо остаётся прежним и интерфейс ещё требует проверки этого маршрута на новых пользователях.

Для первого показа достаточно продемонстрировать общий API-контракт на нескольких листах и ручной разбор изменения. Сборщик документов, импорты всех редакторов и универсальный магазин плагинов не являются необходимыми условиями такого показа.

Содержание авторского рассказа: какой вопрос карта помогает разобрать; почему обычные копии расходятся; как устроены ID и листы; какие операции уже работают; где автор сам столкнулся с ограничениями. Для обсуждения на HN автор должен писать собственным голосом: правила запрещают сгенерированный и отредактированный ИИ текст в комментариях. Не просить голосов и не обещать измеренную пользу без исследования. [Общие правила HN](https://news.ycombinator.com/newsguidelines.html).
