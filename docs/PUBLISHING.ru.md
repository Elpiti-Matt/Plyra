# GitHub, лицензия, счётчик и сопровождение

Предлагаемое место: публичный репозиторий **`ВАШ_АККАУНТ/plyra`**, веб-демо на GitHub Pages, автономный HTML отдельным asset релиза. Название не проверялось на занятость в вашем аккаунте. Репозиторий и релиз пока не созданы: аккаунт не указан, подключённого доступа к GitHub в этой сессии нет.

Не нужен отдельный бэкенд. Исходники полезнее положить в обычный репозиторий, чем оставлять единственным исходником gist с минифицированным HTML. [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) подходит для статической сборки.

## Лицензия

Подробная проверка установленного дерева, различий между HTML и инструментами сборки, а также план перехода на Apache-2.0: [LICENSING.ru.md](LICENSING.ru.md). **Сейчас комплект остаётся MIT.** Apache-2.0 подходит для собственного кода проекта и является предлагаемым вариантом; смена лицензии ещё не выполнена. В исходном пользовательском ZIP лицензии не было, поэтому строка copyright в подготовленном комплекте не подтверждает происхождение прав.

| Материал | Подготовленный вариант | Причина |
|---|---|---|
| Код, учебные графы, README и техническая документация | MIT, файл LICENSE | Простое повторное использование, модификации и встраивание с сохранением notices |
| Сторонние библиотеки | Их исходные лицензии, THIRD_PARTY_NOTICES.txt | MIT проекта не отменяет чужие условия |
| Рабочие статьи | Права зарезервированы до авторской финальной версии | Тексты ещё редакторские, с участием ИИ |
| Самостоятельно завершённые авторские статьи | Рекомендация CC BY 4.0 | Если желательны переводы и перепубликации с атрибуцией |
| Фото котельной из ZIP | Не включено | Во вложении нет проверяемой лицензии или атрибуции |

[MIT](https://choosealicense.com/licenses/mit/) подходит для исследовательского инструмента, который хочется дать другим адаптировать. Apache-2.0 имеет смысл отдельно рассмотреть, если важен явно выраженный патентный грант; копилефт — если цель в обязательном открытии производных. Такая цель в задаче не заявлена, поэтому подготовлена MIT. Перед публичным выпуском в строке copyright можно вместо коллективного `Atlas contributors` указать имя/организацию фактического владельца прав. Это практический выбор оформления, не заключение о принадлежности прав.

## Счётчик без аналитики внутри демо

Рекомендован **счётчик скачиваний release assets**. В GitHub API для каждого asset есть `download_count`; [документация](https://docs.github.com/en/rest/releases/assets). После выбора аккаунта `scripts/configure_repo.py` вставляет [Shields-бейдж](https://shields.io/badges/git-hub-downloads-all-assets-all-releases) в README.

Он считает суммарные скачивания приложенных файлов по релизам. Повторное скачивание одним человеком увеличивает счётчик; скачивание нескольких assets также учитывается несколько раз. Автоматически созданные GitHub source archives, посещения демо и его локальные запуски — другая метрика. Поэтому подпись должна быть «downloads», а не «users».

Дополнительно владелец видит [Insights → Traffic](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/viewing-traffic-to-a-repository): посетителей и клоны за последние 14 дней. Это полезно для оценки запуска, но не замена публичного счётчика скачиваний.

```sh
python scripts/github_stats.py YOUR_ACCOUNT/plyra
```

Скрипт обращается к публичному GitHub API по требованию. Он не включён в HTML, не получает ваши графы и не создаёт фоновое наблюдение. В комплекте проверена обработка контрольного ответа; живые числа появятся только после реального релиза.

Внутри автономного демо нет счётчика посещений. При открытии файла локально приложение не делает сетевых запросов. При открытии GitHub Pages сервер получает запрос страницы и ведёт собственные security logs, включая IP; это прямо описано в документации Pages. Формулировка «совсем ничего никуда не отправляется» относится к работе с графом в локальном файле, а не к доставке сайта через интернет.

## Публикация подготовленного комплекта

1. Завершить ручную проверку из `QA-MANUAL.md` либо явно оставить маркировку release candidate с открытым статусом совместимости. Для основного анонса предпочтительна проверенная версия.
2. Выбрать аккаунт, проверить название и владельца прав. Подключить GitHub, если публикацию должен выполнить ассистент. Не передавать токены в чат.
3. В локальном каталоге выполнить `python scripts/configure_repo.py YOUR_ACCOUNT`. Скрипт заполняет ссылки, но ничего не публикует. Проверить изменения.
4. Создать публичный репозиторий и загрузить исходники, `demo/`, `data/`, документацию и workflows. `node_modules`, `.qa` и `dist` не загружать. Не включать исходные приватные вложения целиком.
5. Проверить workflow **Checks**. Он запускает `npm ci`, тесты и production build. Действия публикации не запускаются автоматически по push.
6. В Settings → Pages выбрать GitHub Actions, затем вручную запустить **Publish demo to GitHub Pages**. Workflow собирает актуальные исходники и публикует `dist`.
7. Создать prerelease **v0.6.1-rc.1** (либо текущую версию из `package.json`, если она уже изменилась). Прикрепить `demo/index.html` под именем `plyra.html` и при желании контрольную сумму с этим же именем файла. Если нужен чистый счётчик скачиваний приложения, выкладывать один HTML как основной asset либо фильтровать по имени; общий бейдж считает все assets.
8. Открыть фактическую ссылку Pages, проверить скачивание и показ счётчика. Нулевой показатель в новый день не является ошибкой; до релиза нельзя показывать выдуманное число.
9. Доработать статьи самостоятельно с учётом `articles/README.md`, заменить ссылки на реальные, сделать реальные скриншоты и только затем отправлять материалы на площадки.

## Минимальное сопровождение

README RU/EN, CHANGELOG, шаблон bug report, CONTRIBUTING, SECURITY, описания формата и ручной QA уже включены. Публичного SLA нет: обозначение «исследовательский прототип» должно остаться и в релизе.

После запуска сначала разбирать потерю данных, ошибки импорта и регрессии мобильной навигации. Просить воспроизводимый минимальный учебный граф, браузер, версию и шаги. Не предлагать пользователям публиковать рабочие базы в issues. Исправление сопровождать регрессией, если оно касается сохранности данных или основного сценария.

Версии: patch для исправлений без изменения формата; minor для совместимых возможностей; новый формат — с явной миграцией и тестом обратной совместимости. Не заменять незаметно файл в уже скачанном релизе: выпускать новый tag и сохранять changelog.

Полезные следующие задачи: реальные browser E2E, формальный провенанс, лучшая ручная работа с границами. RU/ENG уже доступны. Автоматическую кластеризацию и агентскую сборку вики стоит добавлять после проверки базового чтения и переноса данных. При обновлении зависимостей повторять проверку лицензий, особенно состава автономного HTML.
